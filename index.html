C++ 没有运行时反射。typeid 只给出一个名字和一个可比较的 type_info，sizeof 只给出大小，标准库里没有任何东西能在运行时回答"这个类有哪些字段"。但序列化、编辑器属性面板、脚本绑定、控制台命令系统——这些需求全都指向同一件事：需要在运行时按名字读写字段、按名字调用方法。

这篇文章拆解一个约 700 行的 C++17 反射 Demo。它不用宏、不用代码生成、不依赖 RTTI 之外的任何东西，核心机制只有一个：把每个字段和方法的操作，编译期擦除成一组统一签名的函数指针，塞进 std::tuple，再按名字注册到全局表里。

不只讲它怎么工作。我把它编译跑了一遍，也把它跑崩了一次——文章后半部分是三个经过实际验证的缺陷，包括一个必然触发的堆破坏。

一、核心思路：类型擦除成函数指针元组

反射的本质困难在于：Player::hp 是 int，Player::name 是 std::string，Player::position 是 Vec3。类型不同，就没法用同一个容器装它们的访问逻辑。

这个 Demo 的答案是：不要装类型，装操作。任何字段的读写都可以归约成两个统一签名：

// new 的三步
p = new Singleton();
// 展开为：
void* raw = malloc(sizeof(Singleton));  // 1. 分配内存
new(raw) Singleton();                    // 2. 构造（写成员变量）
p = raw;                                 // 3. 赋值指针

// malloc 只有两步
p = (Singleton*)malloc(sizeof(Singleton));
// 展开为：
void* raw = malloc(sizeof(Singleton));  // 1. 分配内存
p = (Singleton*)raw;                     // 2. 赋值指针（强转）

多线程下，步骤 2 和步骤 3 可能被编译器或 CPU 重排：指针已经非空，但对象还没构造完。另一个线程读到非空指针就开始使用，拿到一个"半构造"对象——这就是半构造 BUG 的根因。

SFINAE是C++模板元编程中的一个重要概念，全称是 “Substitution Failure Is Not An Error”（替换失败不是错误）。

游戏网络架构2

 2026.7.31  2026.8.6  269  2 mins

三种主流的网络同步架构

  1. 快照同步 (Snapshot / Step-shot Synchronization)
  2. 帧同步 (Lockstep Synchronization)
  3. 状态同步 (State Synchronization)

快照同步 (Snapshot Synchronization)

服务器绝对权威

工作流程如下3：

  1. 客户端 (Client): 职责非常单一，仅负责采集用户输入 (Input)（如键盘、鼠标操作）并将其发送给服务器。
  2. 服务器 (Server): 作为绝对权威，接收所有客户端的输入，独立地、完整地模拟整个游戏世界。
  3. 同步过程: 服务器以固定的时间间隔（Tick Rate，例如每秒10次）为整个游戏世界拍摄一张快照 (Snapshot)。这张快照包含了该时刻所有关键对象（玩家、AI等）的完整状态（如精确的位置、旋转、速度、血量等）。
  4. 客户端表现: 客户端接收到服务器发来的快照后，不进行任何本地推演或计算，而是像操作“提线木偶 (Puppet/Pawn)”一样，将游戏世界中的所有对象强制更新到快照所描述的状态，然后基于这个状态进行渲染。

关键优化技术

直接应用原始的快照同步会遇到性能瓶颈，因此诞生了两种关键的优化方法。

1. 客户端插值 (Client-Side Interpolation)

  • 问题: 服务器的更新频率（Tick Rate，如10Hz）通常远低于客户端的渲染帧率（Framerate，如60Hz）。如果客户端每一帧都直接跳转到最新的快照状态，画面会显得非常卡顿、不连贯（Jittery）。
  • 解决方案: 客户端在收到两个连续的快照（例如 Snapshot_T1 和 Snapshot_T2）之间，并不会立即应用 T2 的状态。而是在 T1 到 T2 的时间段内，通过插值 (Interpolation) 算法，平滑地将游戏对象从 T1 的状态过渡到 T2 的状态。这使得玩家在客户端看到的是流畅的动画，而非离散的状态跳变。
