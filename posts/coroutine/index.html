C++20 协程在做什么

co_await 不是魔法，是一个堆上的状态机。
 2026.8.6  2026.8.6  674  4 mins

一行 co_await，编译器写了一百行

假设我们要做这样一件事：

  1. 从网络读取配置文件路径
  2. 根据路径读取本地文件
  3. 解析文件内容
  4. 把结果发送回客户端

传统的同步方式

void handle_request(Socket& sock) {
    std::string path = sock.read();        // 阻塞等待网络 IO
    std::string content = read_file(path); // 阻塞等待磁盘 IO
    Data result = parse(content);          // CPU 密集
    sock.write(result);                    // 阻塞等待网络 IO
}

问题：每个阻塞操作都会让整个线程停在那里，无法处理其他请求。

传统解决方案：多线程。

  • 一个请求一个线程
  • 成本：线程创建/销毁开销、栈内存（MB 级）、上下文切换
  • 结果：C10K 问题（见下文）

C10K 问题

“单台服务器如何同时处理 1 万个并发连接？”

当时主流模型是「一连接一线程」：

客户端1     ──► 线程1 (阻塞等待IO)
客户端2     ──► 线程2 (阻塞等待IO)
  ...
客户端10000 ──► 线程10000 ？？？

10,000 个线程的代价：

  • 每个线程默认栈 1–8 MB → 光栈就要几十 GB 内存
  • 线程上下文切换的开销随线程数线性增长
  • 内核调度器在大量线程间协调的额外负担（惊群问题等）

实际到几百个线程就开始显著抖动，根本到不了 1 万。解法方向是——用少量线程驱动大量连接，让 IO 等待不占用线程。

方案 机制 代表
select / poll 轮询 fd 列表 早期 Unix
epoll / kqueue 事件通知，只返回就绪的 fd Linux / BSD
异步 IO + 回调 注册回调，IO 完成才调用 Node.js, libuv
协程 用户态调度，切换代价极低 Go, C++20

void handle_request(Socket& sock) {
    sock.async_read([&sock](std::string path) {
        async_read_file(path, [&sock](std::string content) {
            async_parse(content, [&sock](Data result) {
                sock.async_write(result, [](bool success) {
                    // 终于结束了……
                });
            });
        });
    });
}

问题：

  • 可读性崩溃：逻辑被切成碎片，代码向右偏移
  • 错误处理地狱：每层回调都要独立处理错误
  • 生命周期噩梦：[&sock] 捕获的引用很容易悬垂（sock 可能已经析构）
  • 控制流分裂：for 循环里怎么写异步？没法写

enum class State { ReadPath, ReadFile, Parse, Write, Done };

struct Context {
    State state = State::ReadPath;
    Socket* sock;
    std::string path;
    std::string content;
    Data result;

    void resume() {
        switch (state) {
        case State::ReadPath:
            sock->async_read([this](std::string p) {
                path = std::move(p);
                state = State::ReadFile;
                resume();
            });
            break;
        case State::ReadFile:
            async_read_file(path, [this](std::string c) {
                content = std::move(c);
                state = State::Parse;
                resume();
            });
            break;
        // ... 更多状态
        }
    }
};

问题：

  • 样板代码爆炸：每个异步函数都要写一遍状态机
  • 局部变量变成成员：path、content 必须存在 Context 里
  • 跨挂起点的控制流：if / for / try-catch 都要手动拆解
  • 维护噩梦：加一个步骤要改好几个地方

协程的核心思想：暂停与恢复

协程的本质：让异步代码看起来像同步代码，但不阻塞线程。

struct ComputeFrame {
    int __state = 0;          // 当前在第几个挂起点
    int a, b;                 // 局部变量提升到帧里
    Promise __promise;        // 与外界通信
    SomeAwaitable __tmp1;     // co_await 的临时 awaitable
    SomeAwaitable __tmp2;
};

Task<int> compute() {
    auto* frame = new ComputeFrame();   // 堆分配

    switch (frame->__state) {

    case 0:  // 第一次进入
        frame->__tmp1 = read_async();
        // 问：数据准备好了吗？
        if (!frame->__tmp1.await_ready()) {
            frame->__state = 1;                           // 记录恢复点
            frame->__tmp1.await_suspend(handle);          // 把 handle 注册给 IO
            return frame->__promise.get_return_object();  // 控制权交还
        }
        [[fallthrough]];

    case 1:  // 从第一个 co_await 恢复
        frame->a = frame->__tmp1.await_resume();

        frame->__tmp2 = read_async();
        if (!frame->__tmp2.await_ready()) {
            frame->__state = 2;
            frame->__tmp2.await_suspend(handle);
            return;
        }
        [[fallthrough]];

    case 2:  // 从第二个 co_await 恢复
        frame->b = frame->__tmp2.await_resume();
        frame->__promise.return_value(frame->a + frame->b);
        // …final_suspend
    }
}

关键观察：

  • 每个 co_await 表达式被展开为一个 SomeAwaitable 临时对象，存入协程帧
  • 跨挂起点的局部变量（a、b）被提升到帧里，保证挂起期间依然存活
  • __state 是状态机的"程序计数器"，记录下次从哪个 case 恢复

协程帧布局

编译器为每个协程实例在堆上分配一个协程帧，布局大致如下：

+---------------------------+
| 协程状态 (__state)         |  ← 保存挂起点索引
+---------------------------+
| Promise 对象              |  ← promise_type 实例
+---------------------------+
| 函数参数副本              |  ← 按值/引用捕获的参数
+---------------------------+
| 局部变量                  |  ← 跨挂起点存活的变量
+---------------------------+
| 临时对象                  |  ← awaitable 等临时值
+---------------------------+
| 对齐填充                  |
+---------------------------+
  • 分配：通常通过 operator new 在堆上分配，但可以通过 promise_type::operator new 自定义
  • 生命周期：从协程首次调用创建，到最后一个 coroutine_handle 销毁时释放
  • 大小优化：编译器会做逃逸分析，只保留跨挂起点的变量；不跨挂起点的局部变量仍留在栈上

Task<int> foo(int x) {
    struct Frame {
        int __state = 0;
        Promise __promise;
        int x;       // 参数副本（即使未跨挂起点使用，也需入帧保证生命周期）
        int a, b;    // 局部变量：跨 co_await，必须提升
        SomeAwaitable __awaiter1;
        SomeAwaitable __awaiter2;
    };

    Frame* f = new Frame{.x = x};

    switch (f->__state) {
    case 0:
        f->__awaiter1 = async_read();
        if (!f->__awaiter1.await_ready()) {
            f->__state = 1;
            f->__awaiter1.await_suspend(handle_from_frame(f));
            return f->__promise.get_return_object();
        }
        [[fallthrough]];
    case 1:
        f->a = f->__awaiter1.await_resume();
        f->__awaiter2 = async_compute(f->a);
        if (!f->__awaiter2.await_ready()) {
            f->__state = 2;
            f->__awaiter2.await_suspend(handle_from_frame(f));
            return;
        }
        [[fallthrough]];
    case 2:
        f->b = f->__awaiter2.await_resume();
        f->__promise.return_value(f->a + f->b);
        goto final_suspend;
    }
}

注意：函数参数 x 虽然在这个例子里没有跨挂起点使用，但编译器仍会将其存入协程帧——因为协程的生命周期由 coroutine_handle 管理，而非调用者的栈帧。原始栈帧在协程首次挂起时就销毁了，参数必须随帧迁移到堆上。

小结

编译器替我们做了三件事：

  1. 把局部变量提升到堆上的协程帧
  2. 把 co_await 拆成三步：获取 awaitable → 判断挂起 → 取回结果
  3. 把整个函数体展开为一个 switch-case 状态机
